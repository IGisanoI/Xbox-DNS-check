# Процедура ротации INGEST_TOKEN

Токен приёмника виден в двух местах: `cloud_config.json` у пользователей
десктопной программы и `web/config.js` в опубликованном сайте. Допущение пилота:
спам через видимый токен — приемлемый риск. Ротация — защита, когда риск
перестанет быть приемлемым (спам в листе, чужие отчёты).

## Когда ротировать

- В листе `Reports` появились явно посторонние строки (мусор, флуд).
- Токен утёк за пределы проекта (скриншоты, логи, чужие руки).
- Перед публичной демонстрацией проекта на ревью — по решению Данила.

## Шаги (10 минут)

1. **Новый токен.** Сгенерировать длинную случайную строку, например:
   `python -c "import secrets; print(secrets.token_urlsafe(32))"`
2. **Apps Script.** Открыть проект приёмника → «Параметры проекта скрипта»
   (Project Settings / Script Properties) → изменить свойство `INGEST_TOKEN`
   на новое значение. Старый токен перестаёт работать сразу.
3. **Деплой.** В Apps Script: «Развертывание» → «Управление развертываниями» →
   карандаш у активного веб-приложения → **новая версия** → развернуть.
   Без новой версии `/exec` продолжает работать на старом коде.
4. **Десктоп.** Обновить `token` в `cloud_config.json` (у Данила и у коллег,
   кому раздали программу). Программа читает файл при каждой отправке —
   перезапуск не нужен, но очередь outbox повторит старые отчёты со старым
   токеном и получит отказ; это нормально, они останутся в outbox.
5. **Веб.** Обновить `token` в `web/config.js` и опубликовать (push в
   `docs/` репозитория).
6. **Проверка.** Отправить тестовый отчёт с десктопа и с веб-страницы;
   убедиться, что оба дошли (в листе новые строки), а старый токен отклонён
   (`{"ok":false,"error":"unauthorized"}`).

## Мониторинг между ротациями

- Раз в неделю: открыть `Reports`, смотреть `created_at` и `verdict` —
  мусор виден невооружённым глазом.
- Приёмник отклоняет плохой токен, но НЕ пишет журнал отказов. Если журнал
  понадобится — добавить лист `Rejected` в appendReport_-стиле, это правка Code.gs.
